## `server.js` — HTTP i granice bezpieczeństwa

Ręczny router na czystym `node:http` (bez frameworka), match po `segments`/`method`. Serwuje `public/` (SPA fallback, ETag/no-cache dla kodu, 1 h cache dla logo/favicon). Kluczowe reguły:

- **Proxy `/api/vps/*` → instancja VPS** — dashboard lokalny przełącza widok między `local` a `vps` bez osobnego portu.
- **Blokada zewnętrzna**: request z nagłówkiem `X-Forwarded-For` (czyli przez Tailscale Funnel) dostaje 403 na wszystkim poza `/webhook/*`, `/ask/*` i `/inbox/v1/*`. Dashboard jest dostępny **tylko** przez Tailscale (prywatnie); publiczne są wyłącznie webhooki, endpoint głosowy i tokenowe endpointy skrzynki. **Kontrakt kolejności matcherów: webhook → ask → inbox → guard XFF → api/static** — publiczne endpointy (webhook/ask/inbox) MUSZĄ stać przed guardem (inaczej Funnel dostaje 403 i endpoint jest martwy), a guard przed api/static (inaczej dashboard — w tym prywatne `/api/inbox/members` — robi się publiczny).
- **`POST /ask/:token`** (publiczny, opt-in `ASK_ENABLED=1` — bez niego 403): podwójna autoryzacja token z URL + nagłówek `X-Secret` (`timingSafeEqual`, oba porównania zawsze — czas odpowiedzi nie zdradza, czy token trafiony). Kody błędów TYLKO dla intruzów (403/405/413 bez szczegółów); wszystko „dla człowieka" = 200 text/plain z tekstem (Shortcuts gubi body przy kodzie błędu). Body czytane własnym `readTextBody` (surowy tekst, nie `parseBody`-JSON) z capem 64 KB — bez limitu nieuwierzytelniony intruz streamowałby setki MB → OOM schedulera (body idzie PRZED autoryzacją).
- **Inbox — publiczne vs prywatne**: tokenowe endpointy skrzynki `/inbox/v1/:token/*` (ping/pull/done/send/claim-query) są **publiczne** (przez Funnel, PRZED guardem XFF — patrz kontrakt matcherów). Administracja członkami `/api/inbox/members` (GET/POST/DELETE) jest **prywatna**: siedzi ZA guardem XFF (Tailscale-only, ruch z Funnela z `X-Forwarded-For` nigdy tu nie dotrze) i dodatkowo ma **guard cross-origin** (`isCrossOriginRequest`: `Origin ≠ Host` na żądaniach mutujących → 403) — te endpointy zwracają/obsługują SEKRETY (pełny token, kod zaproszenia), a globalne `ACAO:*` pozwoliłoby stronie `evil.com` czytać odpowiedź z `localhost`; XFF tego nie łapie (żądanie z przeglądarki idzie bez XFF). POST zwraca pełny token JEDNORAZOWO (GET zawsze maskuje), fail-fast 503 gdy brak `WEBHOOK_BASE_URL` (kod zaproszenia byłby bezużyteczny) PRZED utworzeniem członka.
- **Settings powiadomień**: `GET/PUT /api/settings/notifications` (GET zawsze zamaskowany; PUT whitelist 3 kluczy state, tylko stringi, pusty string czyści klucz → fallback env wraca) oraz `POST /api/settings/notifications/push-to-vps` — push robi **serwer** (czyta pełne wartości z własnego state/env), dashboard nigdy nie operuje pełnymi sekretami; statusy: 503 brak VPS, 400 nic do wysłania, 502 pad pusha.
- **Aktualizacja `GET/POST /api/update`** (`lib/updater.js`) — **najgroźniejszy endpoint w całym API**: zdalne pobranie kodu z GitHuba + restart daemona. Siedzi za guardem XFF jak cały dashboard, a POST dodatkowo za wspólnym guardem cross-origin `handleApi` i za serwerową flagą „aktualizacja już trwa" (409) — blokada wyłącznie w przeglądarce ginie przy odświeżeniu strony i odpala drugi odczepiony instalator (na Windowsie: dwa równoległe swapy katalogu z bazą).
- Przy starcie `reapOrphanedRuns()` oznacza osierocone runy `running` (po crashu/restarcie) jako `killed` — inaczej kill-bar w UI wisiałby w nieskończoność.
