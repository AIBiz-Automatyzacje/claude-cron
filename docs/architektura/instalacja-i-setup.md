## Instalatory i setup (z sekcji „Komendy”)

Instalatory (odpalane przez usera, nie w dev-loopie): `install.sh` (macOS), `install.ps1` (Windows), `scripts/install-vps.sh` (Linux/VPS — komponentowy, Obsidian+Puls+Tailscale, flagi `--only-puls`/`--reset`, guard lib-only `CLAUDE_CRON_LIB_ONLY`; dwa NIEZALEŻNE komponenty Team OS: `setup_team_os_hub` = admin stawia hub, `setup_team_os_member` = podłączenie TEJ maszyny do cudzej skrzynki — patrz niżej). `install.ps1` świadomie NIE dostaje ścieżki członka: na Windowsie onboarding idzie przez `setup.mjs`, a duplikat pytania w PowerShellu byłby trzecim miejscem do utrzymania. Ich testy: `install.test.sh`, `install.ps1.Tests.ps1` (od 07.08 odpalalne też na macOS: `pwsh -NoProfile -File install.ps1.Tests.ps1` — brew `powershell`; testy semantyki ścieżek Windows mają skip-guard poza Windows), `scripts/install-vps.test.sh`, `setup.test.mjs`.

**Katalog instalacji jest wolnym wejściem usera** (`ask_install_dir`/`resolve_install_dir` w `install.sh`, `Read-InstallDir`/`Resolve-InstallDir` w `install.ps1`; env `INSTALL_DIR` pomija pytanie, `INSTALL_TTY` to DI wyłącznie dla testów) — więc KAŻDY destrukcyjny konsument tej wartości (przeniesienie katalogu do tmp kasowanego trapem, ubijanie procesów po ścieżce) wymaga własnego guardu; sanityzacja obsługuje cudzysłowy z Findera/Explorera, escape'owane spacje, `~` i ścieżki względne. Port dashboardu rozstrzyga `setup.mjs` (`resolveDashboardPort`) **przed** hookiem i startem serwera: `classifyPortState` łączy bind-test (`probeDashboardPort`, oba adresy) z **zestawem pól kontraktu `/api/status`** (`uptime`, `queue_length`, `total_jobs`, `enabled_jobs`) — luźny substring kazałby uznać cudze API za własną instancję. Wybrany port wypalany w TRZY miejsca naraz (env User-scope, źródło hooka autostartu, `spawnServer`), bo zmiana env nie propaguje się do żyjących procesów.

Setup lokalny (`setup.mjs`) poza pytaniami o workspace/VPS/autostart: zbiera konfigurację powiadomień (Discord webhook, token Telegrama + auto-detekcja chat ID przez `getUpdates`, test-send) do **state DB** i pushuje ją na VPS przez `lib/notify-push.js` (warn przy padzie, nigdy fail setupu); seeduje podstawowe taski (`lib/starter-jobs.js`); instaluje skill **`puls`** z katalogu repo `skills/puls` globalnie do `~/.claude/skills/puls` (kopia, nie symlink — Windows; re-run nadpisuje). Skill uczy agenta Claude Code pracy z REST API Pulsa. Pyta też o kod zaproszenia do skrzynki Team OS (`askInboxInvite` — puste = pomiń): cała sekwencja idzie przez wspólny `runOnboard` ze `scripts/inbox/onboard.mjs`, z guardem `.gitignore` PRZED zapisem tokenu i rolą maszyny `client` (laptop = sync, nigdy auto-reply). Instalator VPS **nie pyta o Discord** i usuwa `DISCORD_WEBHOOK_URL` z unitu systemd — powiadomienia na VPS wymagają pusha z instalacji lokalnej.

Setup zapisuje też DWA kontrakty międzymodułowe, oba **bezwarunkowo** (niezależnie od odpowiedzi o autostart): (1) **`data/version.json`** — rewizja instalacji, którą `server.js` zwraca w polu `version` w `/api/status` (`lib/version.js`; odczyt NIGDY nie rzuca — brak pliku, uszkodzony JSON i błąd I/O dają ten sam kształt `revision:'unknown'`); (2) **katalog instalacji w dwóch miejscach naraz** — `env.PULS_HOME` w `{workspace}/.claude/settings.json` (idempotentny merge `mergeEnvIntoSettings`, lustro `mergeHookIntoSettings`; działa tylko w sesjach Claude Code z tego workspace'u) **oraz** wskaźnik `~/.claude-cron-home` o stałej nazwie (konwencja `~/.claude-cron-oauth-token`; działa dla KAŻDEGO procesu). Bez tego skille w vaulcie (`deleguj`) nie znajdą `data/inbox.env` — a **zgadywanie `$HOME/claude-cron` jest odrzucone**, bo katalog instalacji to wolne wejście usera. Uszkodzony `settings.json` = fail-fast (nie nadpisujemy cudzych permissions/hooków), pad zapisu wskaźnika = warn.

## Runtime — twarde wymaganie Node

Aplikacja stoi na wbudowanym `node:sqlite` (klasa `DatabaseSync`), stabilnym bez flagi dopiero od **Node 22.13**. `engines` wymusza `>=22.13 <25`.

- `lib/runtime-guard.js` **MUSI być pierwszym `require` w `server.js`** — robi fail-fast z czytelnym komunikatem PRZED jakimkolwiek top-level `require('node:sqlite')` (który na starym Node rzuca nieczytelnym błędem).
- Po migracji `db.assertDbReturnsNumbers()` robi smoke-test: niektóre buildy zwracają `COUNT(*)`/`SUM(...)` jako BigInt zamiast number — wtedy arytmetyka i `JSON.stringify` cicho się psują. Fail-fast zamiast cichej korupcji.
- Instalatory pobierają **przenośny Node 22.17.0** do `.node/` (weryfikacja SHA256) — nie dotykają systemowego Node ani PATH. Wersja pinowana w `setup.mjs` (`NODE_VERSION`) musi być spójna z `install.sh`/`install.ps1`.
- Po postawieniu portable Node, PRZED handoffem do `setup.mjs`, bootstrap odpala `npm install --omit=dev` **npm-em z portable Node** (`ensure_dependencies`/`Install-Dependencies`) — bootstrap NIE przenosi `node_modules` ze starej instalacji, więc świeży katalog zawsze wymaga instalacji. Portable Node musi być na czole PATH, bo install-script `koffi` (cnoke) spawnuje `node`. Bez build-tools: `koffi` bundluje prebuilty (w tym `win32_*`); deterministycznie przez `package-lock.json`. Historycznie ten krok zgubił się przy przepisaniu na portable Node — brak go = `setup.mjs` pada na `Cannot find module 'gray-matter'` przy seedowaniu starter-tasków.
