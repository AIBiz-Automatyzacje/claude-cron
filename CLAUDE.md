# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Czym jest projekt

**Puls** — scheduler agentów AI (Claude Code). User ustawia joby (skill/prompt + harmonogram cron), a serwer w tle odpala CLI `claude` o wybranej porze, zbiera output i pokazuje historię w retro-arcade dashboardzie na `localhost:7777`. Działa lokalnie (macOS/Windows) oraz 24/7 na VPS (Linux), spięte przez Tailscale.

> **Nazwa produktu to Puls, ale identyfikatory techniczne wciąż używają starej nazwy `claude-cron`** — nie zmieniaj ich pochopnie: nazwa w `package.json`, plik bazy `data/claude-cron.db`, label launchd `com.claude-cron.scheduler`, task Windows `ClaudeCron`, zmienne środowiskowe `CLAUDE_CRON_*`, ścieżka instalacji `~/claude-cron`. Zmiana którejkolwiek psuje istniejące instalacje. "Puls" to warstwa prezentacji (README, UI, logi startowe).

## Komendy

```bash
npm start                 # uruchom serwer (node --disable-warning=ExperimentalWarning server.js)
npm test                  # wszystkie testy (node:test, wbudowany runner — zero zależności testowych)
node --test lib/db.test.js         # pojedynczy plik testowy
node --test setup.test.mjs         # testy setupu (ESM)
node --test scripts/inbox/inbox-pull.test.mjs   # testy skryptów Team OS inbox (ESM)
```

Nie ma buildu, bundlera, lintera ani typecheckera. Backend to czysty CommonJS, frontend to vanilla JS ładowany bezpośrednio przez `<script>` (patrz `public/index.html`). Testy używają wyłącznie wbudowanego `node:test` + `node:assert`.

Instalatory (odpalane przez usera, nie w dev-loopie): `install.sh` (macOS), `install.ps1` (Windows), `scripts/install-vps.sh` (Linux/VPS — komponentowy, Obsidian+Puls+Tailscale, flagi `--only-puls`/`--reset`, guard lib-only `CLAUDE_CRON_LIB_ONLY`; dwa NIEZALEŻNE komponenty Team OS: `setup_team_os_hub` = admin stawia hub, `setup_team_os_member` = podłączenie TEJ maszyny do cudzej skrzynki — patrz niżej). `install.ps1` świadomie NIE dostaje ścieżki członka: na Windowsie onboarding idzie przez `setup.mjs`, a duplikat pytania w PowerShellu byłby trzecim miejscem do utrzymania. Ich testy: `install.test.sh`, `install.ps1.Tests.ps1` (Pester), `scripts/install-vps.test.sh`, `setup.test.mjs`.

**Katalog instalacji jest wolnym wejściem usera** (`ask_install_dir`/`resolve_install_dir` w `install.sh`, `Read-InstallDir`/`Resolve-InstallDir` w `install.ps1`; env `INSTALL_DIR` pomija pytanie, `INSTALL_TTY` to DI wyłącznie dla testów) — więc KAŻDY destrukcyjny konsument tej wartości (przeniesienie katalogu do tmp kasowanego trapem, ubijanie procesów po ścieżce) wymaga własnego guardu; sanityzacja obsługuje cudzysłowy z Findera/Explorera, escape'owane spacje, `~` i ścieżki względne. Port dashboardu rozstrzyga `setup.mjs` (`resolveDashboardPort`) **przed** hookiem i startem serwera: `classifyPortState` łączy bind-test (`probeDashboardPort`, oba adresy) z **zestawem pól kontraktu `/api/status`** (`uptime`, `queue_length`, `total_jobs`, `enabled_jobs`) — luźny substring kazałby uznać cudze API za własną instancję. Wybrany port wypalany w TRZY miejsca naraz (env User-scope, źródło hooka autostartu, `spawnServer`), bo zmiana env nie propaguje się do żyjących procesów.

Setup lokalny (`setup.mjs`) poza pytaniami o workspace/VPS/autostart: zbiera konfigurację powiadomień (Discord webhook, token Telegrama + auto-detekcja chat ID przez `getUpdates`, test-send) do **state DB** i pushuje ją na VPS przez `lib/notify-push.js` (warn przy padzie, nigdy fail setupu); seeduje podstawowe taski (`lib/starter-jobs.js`); instaluje skill **`puls`** z katalogu repo `skills/puls` globalnie do `~/.claude/skills/puls` (kopia, nie symlink — Windows; re-run nadpisuje). Skill uczy agenta Claude Code pracy z REST API Pulsa. Pyta też o kod zaproszenia do skrzynki Team OS (`askInboxInvite` — puste = pomiń): cała sekwencja idzie przez wspólny `runOnboard` ze `scripts/inbox/onboard.mjs`, z guardem `.gitignore` PRZED zapisem tokenu i rolą maszyny `client` (laptop = sync, nigdy auto-reply). Instalator VPS **nie pyta o Discord** i usuwa `DISCORD_WEBHOOK_URL` z unitu systemd — powiadomienia na VPS wymagają pusha z instalacji lokalnej.

## Runtime — twarde wymaganie Node

Aplikacja stoi na wbudowanym `node:sqlite` (klasa `DatabaseSync`), stabilnym bez flagi dopiero od **Node 22.13**. `engines` wymusza `>=22.13 <25`.

- `lib/runtime-guard.js` **MUSI być pierwszym `require` w `server.js`** — robi fail-fast z czytelnym komunikatem PRZED jakimkolwiek top-level `require('node:sqlite')` (który na starym Node rzuca nieczytelnym błędem).
- Po migracji `db.assertDbReturnsNumbers()` robi smoke-test: niektóre buildy zwracają `COUNT(*)`/`SUM(...)` jako BigInt zamiast number — wtedy arytmetyka i `JSON.stringify` cicho się psują. Fail-fast zamiast cichej korupcji.
- Instalatory pobierają **przenośny Node 22.17.0** do `.node/` (weryfikacja SHA256) — nie dotykają systemowego Node ani PATH. Wersja pinowana w `setup.mjs` (`NODE_VERSION`) musi być spójna z `install.sh`/`install.ps1`.
- Po postawieniu portable Node, PRZED handoffem do `setup.mjs`, bootstrap odpala `npm install --omit=dev` **npm-em z portable Node** (`ensure_dependencies`/`Install-Dependencies`) — bootstrap NIE przenosi `node_modules` ze starej instalacji, więc świeży katalog zawsze wymaga instalacji. Portable Node musi być na czole PATH, bo install-script `koffi` (cnoke) spawnuje `node`. Bez build-tools: `koffi` bundluje prebuilty (w tym `win32_*`); deterministycznie przez `package-lock.json`. Historycznie ten krok zgubił się przy przepisaniu na portable Node — brak go = `setup.mjs` pada na `Cannot find module 'gray-matter'` przy seedowaniu starter-tasków.

## Architektura backendu (`lib/`)

Przepływ joba: **cron/webhook/manual → kolejka runów w DB → picker (do `max_concurrent` runów równolegle) → executor → aktualizacja runu → opcjonalnie powiadomienia (Discord/Telegram).**

- **`config.js`** — jedyne źródło stałych i env-varów (`CLAUDE_CRON_PORT` 7777, `CLAUDE_CRON_VPS_URL`, `CLAUDE_CRON_WORKSPACE`, `DISCORD_WEBHOOK_URL`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `WEBHOOK_*`, `ASK_*` — patrz `ask.js`). `MIN/MAX_NODE_VERSION` żyją tu, żeby `runtime-guard` nie ciągnął `node:sqlite`. Override'y dla testów HTTP na żywym procesie serwera (in-process settery nie sięgają spawnowanego dziecka): `CLAUDE_CRON_DB_PATH` (ścieżka bazy zamiast `data/claude-cron.db`), `CLAUDE_CRON_CLAUDE_BIN` (binarka CLI zamiast `claude` — atrapa w testach).
- **`db.js`** — cała warstwa SQLite. `getDb()` leniwie otwiera połączenie i woła `migrate()` przy **każdym** starcie. Schemat: `jobs`, `runs`, `state` (key-value). Migracje przez `ALTER TABLE ... ` w try/catch (idempotentne). **Backfill danych owinięty sentinelem w `state`** (np. `wake_backfill_done`), bo `migrate()` leci co boot — gołe `UPDATE` clobberowałoby świadome opt-outy usera.
- **`scheduler.js`** — `croner` planuje joby w **lokalnej strefie** (`Intl...timeZone`). **Kolejka jest RÓWNOLEGŁA** (do lipca 2026 był jeden globalny slot — to zdanie już nie obowiązuje): pętla drain `processQueue` startuje tyle runów, ile przepuści czysty picker `pickEligibleRuns` (zero I/O, zero `Date.now()` — wzorzec `computeMissedJobs`). Reguły pickera w kolejności: **(1) limit `max_concurrent`** — klucz w `state`, default 3, **per maszyna** (każda instancja ma własny SQLite), czytany w MOMENCIE picku (wzorzec `notify-config.js`, zmiana z dashboardu bez restartu), sufit 10 z API (`sanitizeMaxConcurrent` odrzuca śmieć komunikatem, `resolveMaxConcurrent` przy odczycie ze `state` cicho schodzi do defaultu — limit 0 zatrzymałby scheduler bez słowa); **(2) slot rezerwowy** — zadania długie mają budżet `max(1, limit-1)`, żeby run krótki (inbox sync co minutę) nigdy nie czekał za długim; **(3) jeden run per `job_id`** (dawniej gwarantował to globalny slot — dziś jawna reguła, inaczej sync co 1 min nałożyłby się sam na siebie); **(4) wyłączność automatyczna** po tym samym `skill_name` albo `command` (puste wartości NIE są kluczami — inaczej wszystkie script-joby blokowałyby się nawzajem); **(5) wyłączność deklaratywna** po `lock_group` (kolumna w `jobs`; konwencja: grupa = współdzielony ARTEFAKT, np. `dashboard`, nigdy „cały vault" — to odtworzyłoby stary globalny slot). Konflikt = odroczenie, nie fail: run zostaje `queued`, skan po `id ASC` daje FIFO w obrębie każdej blokady. **Klasyfikacja krótki/długi jest z POMIARU, nie z `job_type`** — `classifyJob` bierze medianę (nie średnią) czasów ostatnich 10 **udanych** runów, próg 60 s; brak historii = długi (fail-safe). Dane z żywej bazy obalają podział po `job_type`: najdłuższy job systemu (747 s) to `script`, a 18-sekundowy to `claude`. **Dzwonek `ringNewWorkBell`**: `processQueue` wołany przy pracującej pętli nie jest no-opem — budzi `Promise.race`, więc dokolejkowany run rusza natychmiast, gdy jest wolny slot, zamiast czekać na koniec cudzego runu (bez tego równoległość byłaby ozdobą). Retry po failu przez `max_retries`. **Missed-job detection**: heartbeat zapisuje `last_active_at` co 60 s; po restarcie `computeMissedJobs()` (czysta, testowalna) sprawdza, które joby z `run_on_wake=1` przegapiono podczas downtime'u i kolejkuje je jako `wake`. Strefa w `computeMissedJobs` MUSI być ta sama co w `scheduleJob`. **Karencja po wybudzeniu**: po wykryciu pobudki pętla wstrzymuje START runów o `WAKE_GRACE_MS = 45 s` (sieć wraca wolniej niż proces — bez tego joby padają na `ENOTFOUND`); retry bez zmian, ścieżka bez wybudzenia jest bit-w-bit dzisiejsza (zero `await`, zero zapytania do DB). Dwa źródła detekcji: luka między tyknięciami heartbeatu (sen maszyny przy żyjącym procesie) i `detectWakeFromDowntime()` w `start()` (reboot; MUSI biec przed `detectMissedJobs`/`startHeartbeat`, bo heartbeat nadpisuje ślad downtime'u). Stan wybudzenia żyje w pamięci procesu, nie w `state`. **Pułapka progu**: `isWakeGap` dostaje próg jawnie i musi być ostro większy od okresu tykania po stronie wołającego (heartbeat tyka co 60 s → próg 120 s) — `gap > period` bierze KAŻDE normalne tyknięcie za wybudzenie i zamraża kolejkę; detekcja siedzi też w `processQueue`, nie tylko w callbacku heartbeatu, bo po pobudce kolejność zaległych timerów nie jest twoja. **Retention**: co godzinę kasuje udane runy jobów `routine=1` starsze niż 24 h (fail/timeout/killed zostają na zawsze).
- **`claude-spawn.js`** — wspólny helper spawnu CLI `claude`, reużywany przez `executor.js` (joby) i `ask.js` (asystent głosowy). Żyje tu wyłącznie to, co MUSI być identyczne po obu stronach: czysty env (strip `CLAUDE_CODE*`/`CLAUDECODE`, żeby spawnowany CLI nie myślał, że jest zagnieżdżony; token OAuth z `~/.claude-cron-oauth-token` wstrzykiwany PO stripie), resolve binarki (Windows: `where claude`, fail-fast zamiast fallbacku `shell:true` — ryzyko command injection z publicznych payloadów) i opcje spawnu (`cwd: WORKSPACE_DIR`). Argumenty CLI buduje wywołujący. Override binarki dla testów: `setClaudeBin` (wzorzec `db.setDbPath`).
- **`executor.js`** — spawn CLI `claude --dangerously-skip-permissions --output-format stream-json -p <prompt>` (przez `claude-spawn.js`). Prompt = `/skill` + `arguments` + `webhook_payload`. Trzy warstwy timeoutów: total, idle (reset na każdym chunku stdout; per-job przez kolumnę `idle_timeout_ms`, fallback stała 5 min — joby z subagentami potrzebują więcej), watchdog wall-clock (przeżywa sen Maca). macOS: `caffeinate` blokuje idle-sleep na czas runu. Windows: `taskkill /T /F` (drzewo procesów). Drugi tryb: **`job_type: 'script'`** — odpala `node <command>` bez CLI Claude; script-joby dziedziczą env daemona.
- **`ask.js`** — asystent głosowy za `POST /ask/:token`: pytanie text/plain → spawn CLI (`--output-format text --model sonnet`) → odpowiedź synchronicznie w ≤ `ASK_TIMEOUT_MS` (55 s, limit cierpliwości Shortcuts) albo **odczepienie w tło** (bez killa — zero podwójnych wykonań; wynik wraca powiadomieniem Discord/Telegram wg flag joba-teczki). Bramki wejścia w kolejności auth → rate limit (10/min) → lock sync (1 naraz) → sloty tła (3); stan współbieżności in-memory (świadomie zero agregatów SQL — pułapka BigInt). Każdy `/ask` = run joba-teczki „Asystent głosowy" (`trigger_type:'ask'`, `routine=1`, poza kolejką schedulera; get-or-create po `name`, nigdy nie nadpisuje flag usera). Gwarancja „nigdy cisza" dla odczepionych: idempotentny `finalizeAskRun` (świeży odczyt DB przed zapisem) + bezpiecznik `ASK_MAX_MS` (10 min, kill drzewa) + ❌ „przerwane przez restart" ze startu serwera (reaper zwraca zebrane runy). Env: `ASK_ENABLED` (opt-in, tylko `=1`), `ASK_TOKEN`/`ASK_SECRET` (wyłącznie env, zero defaultów; rotacja = restart daemona), `ASK_TIMEOUT_MS`, `ASK_MAX_MS`.
- **`platform.js`** — autostart per-OS: macOS = plist launchd, Windows = Task Scheduler (`schtasks`). Zwraca `getStatus()` dla dashboardu. Plist macOS powstaje z czystego `buildPlist({label, repoDir, nodeBin, logFile, env})`: wrapper `/bin/sh -c` z `cd <repo> && exec <node> … server.js` (jedno miejsce na cwd i flagi), **logi w `~/Library/Logs/claude-cron/`, NIE w drzewie repo** (repo stoi w `~/Documents`, a launchd nie ma zgody TCC → agent padał na `EX_CONFIG 78` bez wpisu w logu, bo logu nie było gdzie zapisać; `installMac()` tworzy katalog PRZED `load`), **Node z `.node/`, nie `which node`** (launchd startuje z minimalnym PATH), whitelist `PLIST_ENV_KEYS` (klucz pusty jest POMIJANY — pusty `CLAUDE_CRON_VPS_URL` udaje skonfigurowany i myli diagnozę proxy), `escapeXml` + `shellQuote` (katalog instalacji to wolne wejście usera). Etykieta kanoniczna `com.claude-cron.scheduler` zostaje; ręcznie postawiony `com.claude-cron.daemon` żyje jako `LEGACY_PLIST_LABELS` — `getStatus()` go rozpoznaje, `installMac()` unloaduje i kasuje PRZED `load` nowego (dwa agenty biją się o port 7777). `getStatus()` decyduje po **kolumnie PID** z `launchctl list` i dopasowaniu po CAŁEJ etykiecie, nie po substringu (`!out.includes('-')` zwracało `running:false` zawsze — myślnik siedzi w nazwie `claude-cron`). I/O wstrzykiwalne (`REAL_IO`), bo kontraktem jest KOLEJNOŚĆ kroków. **Moduł NIE jest wpięty w ścieżkę usera** — autostart na Macu robi dziś hook Claude Code z `setup.mjs`; dołożenie launchd bez wygaszenia hooka daje dwa mechanizmy wskrzeszające serwer na tym samym porcie (decyzja produktowa odłożona, patrz `docs/completed/rownolegle-joby/`).
- **`skills.js`** — skanuje `SKILL.md` (frontmatter przez `gray-matter`) z trzech źródeł z priorytetem **project > user > plugin**: workspace `.claude/skills`, `~/.claude/skills`, oraz pluginy z `~/.claude/plugins/installed_plugins.json`.
- **`webhook.js`** — matching tokenów z URL: `matchWebhookToken` (`/webhook/:token`) i bliźniaczy `matchAskToken` (`/ask/:token`).
- **Powiadomienia** (`discord.js`, `telegram.js`, `notify-format.js`, `notify-config.js`, `notify-push.js`) — dwa symetryczne kanały per-job (flagi `discord_notify`/`telegram_notify`). Wspólne formatowanie w `notify-format.js`: `extractResult` (wpis `type:'result'` ze stream-json) + `smartSplit` (chunki: Discord ≤2000, Telegram ≤4096, plain text bez parse_mode). Executor woła `notifyRunOutcome`: ✅ po sukcesie (**ale joby `routine=1` tłumią sukcesy** — flaga kanału na jobie routine znaczy „alarmuj o failach", inaczej sync co 1 min = 1440 powiadomień/dzień), ❌ po **ostatecznym** failu/timeoucie (po wyczerpaniu retry — okno liczone przez `db.countRecentFailedRuns`, TA SAMA definicja co retry w schedulerze), `killed` bez powiadomienia. `notify-config.js` rozwiązuje konfigurację w **czasie wysyłki** (nie przy require — zmiana z dashboardu działa bez restartu) z priorytetem **state (DB) > env** (env to fallback dla starych instalacji); pusty string w state = "brak", NIE nadpisuje env. `notify-push.js` wypycha pełną konfigurację na VPS (PUT + potwierdzenie GET-em; kontrakt `{ok, reason}`, nigdy nie rzuca). Sekrety w state leżą plaintext (świadoma decyzja — poziom zaufania jak shell RC); API zwraca wyłącznie maski (configured + ostatnie 4 znaki).
- **`starter-jobs.js`** + **`templates/starter-jobs.json`** — seed 4 jobów startowych w setupie lokalnym (jedno pytanie `[T/n]`), NIE w `migrate()` (backfill w migrate clobberowałby decyzje usera co boot). Idempotencja po `name`, szablon bez dostępnego skilla pomijany z powodem; brak seedu na VPS.
- **`inbox-seed.js`** — przy starcie daemona seeduje job Team OS (patrz niżej) **rozłącznie wg roli maszyny** (`state.inbox_role`): `agent` → wyłącznie „Team OS — asystent auto-reply" (od razu `enabled: 1` — decyzję podjął instalator, więc job wyłączony po instalacji byłby tylko mylącym artefaktem); `client` **albo brak flagi** → wyłącznie „Team OS — inbox sync" (script-job co 1 min). Oba `routine=1`, `telegram_notify=1` = alarm o failach. Seed TYLKO gdy inbox skonfigurowany (`INBOX_HUB_URL` + `INBOX_TOKEN` przez env-loader); nigdy nie rzuca; **wyłącznie `createJob` gdy joba brak, ZERO `UPDATE`** — seed leci co boot, więc „naprawianie" istniejącego joba pod rolę clobberowałoby ręczne wyłączenia usera (dlatego po ZMIANIE roli stary job zostaje włączony, a `onboard.mjs` mówi o tym wprost). **Pułapka**: `loadEnv` skryptów mutuje `process.env` — seed robi snapshot i przywraca go, bo script-joby dziedziczą env daemona i mutacja zamroziłaby konfigurację `INBOX_*` na moment startu.

## Team OS — Skrzynka (hub `lib/inbox-*.js` + klienci `scripts/inbox/`)

Podsystem wymiany wiadomości między członkami zespołu (typy `task`/`query`/`reply`/`close`, statusy `pending`/`delivered`/`done`) z UI w **vaultcie Obsidiana** (plik Skrzynka.md + banner na dashboardzie). Architektura **hub-and-spoke**: **Puls na VPS-ie admina jest JEDYNYM procesem piszącym** do bazy skrzynki; klienci (`scripts/inbox/`) nie dotykają jej bezpośrednio — robią `fetch` do wersjonowanego API `/inbox/v1/:token/*` przez **Tailscale Funnel**. Transport docelowy = hub; publiczny Postgres (`INBOX_DB_URL`+`INBOX_USER`, `schema.sql`, `pg`) jest **wycofany** — pliki są w trakcie wygaszania (usuwane po zweryfikowanej migracji + decommissionie operatora, patrz Faza 4 planu).

- **Tożsamość = token per członek** (tabela `members`): klient NIE deklaruje kim jest — hub wyprowadza `user` z trafionego tokenu. Odwołanie dostępu jednej osoby = skasowanie jednego tokenu (`revokeMember`), bez rotacji u wszystkich (kontrast z jednym wspólnym hasłem Postgresa). Onboarding = wklejenie jednego **kodu zaproszenia** `puls-inbox:<funnel-url>#<token>` (zero connection stringów, zero Tailscale po stronie członka).
- **Rola maszyny — `state.inbox_role` (`client` | `agent`), jedna flaga zamiast dwóch booleanów.** Rozstrzyga, KTÓRY job seeduje daemon (patrz `inbox-seed.js`). **Ustawiana WYŁĄCZNIE przez instalatory** (`setup.mjs` → zawsze `client`; `onboard.mjs` wołany z `install-vps.sh` → `client` albo `agent`) i **nigdy nie backfillowana w `migrate()`** — `migrate()` leci co boot, więc gołe `UPDATE` clobberowałoby ręczne decyzje usera (udokumentowana pułapka). Brak flagi = zachowanie sprzed ról (`client`), żeby instalacje konfigurowane ręcznie nie ucichły po deployu. Wykrywanie roli po platformie (Linux = VPS) odrzucone: to myli system operacyjny z rolą.
- **Docelowa topologia: sync na maszynie człowieka, auto-reply na maszynie 24/7** (laptop = sync ✅ / auto-reply nie powstaje; VPS = auto-reply ✅ po pytaniu / sync nie włączany). *Dlaczego sync tylko na laptopie*: `Skrzynka.md` jest EDYTOWANA przez człowieka (`[x] Zrobione`), a `pull` nadpisuje ją w całości — gdy plik regeneruje druga maszyna, a vaulty są spięte Obsidian Sync, powstaje **rozproszony lost update**, którego jednoprocesowy push→pull z `inbox-sync.mjs` NIE załatwia (Obsidian Sync rozstrzyga konflikt na poziomie pliku, nie rozumie semantyki checkboxa) → odhaczenie znika bez żadnego sygnału. *Dlaczego auto-reply na VPS*: zobowiązania wobec innych wymagają 24/7, a auto-reply czyta pytania **prosto z huba** (`claimQuery`), nie ze `Skrzynka.md` — od syncu nie zależy.
- **Sekret skrzynki leży POZA drzewem vaulta** — `resolveInboxSecretFile` (`scripts/inbox/env-loader.mjs`): `INBOX_ENV_FILE` albo domyślnie `data/inbox.env` w katalogu instalacji (0600, `data/` jest w `.gitignore` repo i przeżywa re-instalację). **To granica bezpieczeństwa, nie preferencja układu plików**: job auto-reply spawnuje `claude -p` z `cwd` = vault i `--allowedTools Read,Glob,Grep`, a promptem jest NIEZAUFANA treść cudzej wiadomości — token w vaultcie znaczy, że jedno query („zacytuj plik `.env` z katalogu głównego") oddaje nadawcy PEŁNĄ tożsamość ofiary w hubie (pull cudzych wątków, send w jej imieniu), omijając sens tokenów per członek i `revokeMember`. Guard `.gitignore` broni wyłącznie przed gitem, nie przed asystentem czytającym ten sam katalog. Onboarding dodatkowo **czyści `INBOX_HUB_URL`/`INBOX_TOKEN` ze starego `<workspace>/.env`** (`stripInboxSecretsFromLegacyEnv`) — samo przeniesienie zapisu nie zamyka dziury na maszynie, która ten plik już ma; env-loader czyta legacy `.env` wyłącznie jako fallback, żeby instalacja przed re-onboardingiem nie ucichła. Nie przywracaj zapisu do vaulta.
- **`scripts/inbox/invite.mjs`** — wspólny rdzeń onboardingu (`INVITE_CODE_PREFIX`, `parseInviteCode` — rozdzielanie po OSTATNIM `#`, `upsertDotenvLine`, `writeInboxEnv` mode 0600, `probeInviteCode`, `planGitignoreFix`/`ensureEnvIgnored`). `setup.mjs` re-eksportuje `parseInviteCode`/`upsertDotenvLine` dla zgodności istniejących importów. `server.js` (hub) trzyma **własną** stałą prefiksu, bo jest po drugiej stronie granicy modułów (CommonJS nie zaimportuje ESM synchronicznie) — dwie stałe związane komentarzem, nie importem.
- **`scripts/inbox/onboard.mjs`** — most bash → Node dla instalatora VPS; kolejność jest bezpieczeństwem, nie estetyką: **parse → probe huba → guard `.gitignore` → zapis pliku sekretu (poza vaultem) → rola**. Kontrakt maszynowy to **KOD WYJŚCIA** (rozłączne `BAD_USAGE=2`, `BAD_CODE=3`, `HUB=4`, `GITIGNORE=5`, `WRITE=6`; `1` zarezerwowane dla nieobsłużonego wyjątku Node) plus JEDNA linia `[ok]/[warn]/[error]` dla człowieka — **bash nigdy nie parsuje tekstu**, bo komunikaty zmieniają się przy każdej korekcie językowej. Sekrety w komunikatach redagowane (`redactToken`): token siedzi w ŚCIEŻCE `/inbox/v1/:token/ping`, a `undici` osadza pełny URL w powodach błędów.
- **Guard `.gitignore` przed zapisem sekretu (fail-closed).** Vault bywa repo z automatycznym commitem, a instalator dotyka w nim `.env` (czyszczenie legacy — patrz wyżej; historycznie: zapis tokenu; realny wyciek 07.2026: wzorzec `.env` nie łapie kopii `.env.bak.<ts>`). Dlatego PRZED zapisem pytamy **`git check-ignore` o EFEKT** (exit-code), nie czytamy treści `.gitignore` — tylko git zna prawdę o negacjach, wzorcach z katalogów nadrzędnych i `core.excludesFile`. Sondujemy `.env` **oraz** syntetyczne `.env.bak.x`, naprawiamy dopisując `.env*` do `<workspace>/.gitignore` i **pytamy gita PONOWNIE**. Świadomie bez `--no-index`: plik już śledzony w indeksie ma być raportowany jako NIE-ignorowany (dopisanie wzorca go nie odśledzi). Statusy `unfixable` i `unknown` (brak gita / błąd gita — „nie wiem" ≠ „to nie repo", vault bywa commitowany z drugiej maszyny) = **token NIE zapisany**, instalacja leci dalej z instrukcją.
- **Ścieżka członka w `install-vps.sh`** (`setup_team_os_member`, niezależna od huba): odpowiedź „t" na pytanie o hub stawia **WŁASNY hub** — pomyłka daje dwie skrzynki, które nigdy się nie zobaczą; „N" prowadzi wprost do pytania o kod zaproszenia (przez `ask_tty`, puste = pomiń). Admin nie przepisuje kodu z ekranu — instalator używa świeżego `TEAM_OS_INVITE_CODE` z `setup_team_os_hub`. Na obu ścieżkach pytanie „czy ta maszyna ma odpowiadać za zespół?" (domyślnie **N** — `ask_tty` bez tty bierze default, a `T` cicho włączyłby agenta odpowiadającego w imieniu właściciela vaulta) rozstrzyga rolę. Onboarding leci jako user `claude`, nie root (`data/inbox.env` i `data/claude-cron.db` należą do usera daemona). Kolejność: zapis sekretu + rola **PRZED** restartem serwisu — `inbox-seed` czyta flagę dopiero przy starcie, a env nie propaguje się do żyjących procesów. Każdy pad = `warn` + kontynuacja, **nigdy `fail`/ERR** — to opcjonalny krok finału, a rollback odwinąłby zweryfikowaną instalację.
- **`lib/inbox-db.js`** — warstwa SQLite huba, plik **`data/inbox.db` (OSOBNY od `claude-cron.db`)** — skrzynka to inna domena danych i inny cykl życia (współdzielona przez zespół vs stan schedulera), izolacja upraszcza backup/rewokację i nie miesza migracji. **Jedyne miejsce granicy JSON `payload`** (parse/stringify TYLKO tu — powyżej payload jest zawsze OBIEKTEM). **Idempotencja i atomowość siedzą tutaj**: `markDone` czyta świeży wiersz z DB (nie ufa obiektowi z pamięci — learned pattern) i robi transakcję reply+`done` (task/Zrobione); `claimQuery` to atomowy claim jednym `UPDATE ... WHERE id = (podzapytanie) RETURNING` (marker `payload.auto_reply_attempted`). Smoke-test typów agregatów po `migrate()` (pułapka BigInt node:sqlite). Bo cała logika trudna jest po stronie huba, klienci robią głupie żądania i retryują bezpiecznie.
- **`lib/inbox-api.js`** — czysta funkcja `handleInboxRequest({token, action, method, rawBody})` nad `inbox-db` (I/O to cienka skorupa w `server.js`). Granica bezpieczeństwa: `timingSafeEqual` tokenu z URL po **WSZYSTKICH** tokenach członków (brak `break` — czas nie zdradza trafienia), cap body 64 KB (413 zanim intruz wypompuje setki MB), walidacja każdego inputu na granicy, pole `v:1` w KAŻDEJ odpowiedzi (detekcja driftu wersji), kody intruzów (403/404/405/413) bez treści. **Rate limit 60/min per token — świadomie NIE 10/min z `/ask`**: rytm zespołu (sync pull+push + auto-reply + retry ≈ 6 req/min) × ~10 zapasu; 10/min ucięłoby normalną pracę. Stan rate-limitu in-memory (zero agregatów SQL — pułapka BigInt). Endpointy: `ping`/`pull`/`done`/`send`/`claim-query`.
- **`scripts/inbox/inbox-client.mjs`** — klient `fetch` (zastąpił bezpośrednie `pg`). Weryfikuje `v:1`, robi **1 retry na timeout/5xx TYLKO dla akcji idempotentnych** (pull/done/claim-query/ping); **`send` jest bez retry** — to goły INSERT ze świeżym `randomUUID()` bez klucza dedup, więc timeout PO commicie ma nieznany wynik i ponowienie zdublowałoby wiadomość. Konfiguracja czytana z `process.env` W MOMENCIE wywołania (`INBOX_HUB_URL` + `INBOX_TOKEN`; stare `INBOX_DB_URL`/`INBOX_USER` wycofane) — env żyjącego procesu bywa nieświeże (learned pattern).

Klienci-skrypty (ESM, odpalane jako script-joby Pulsa; renderują/parsują vault, transport przez `inbox-client.mjs`, zero CLI Claude poza auto-reply):

- **`inbox-sync.mjs`** — entry point joba: sekwencyjnie push → pull **w jednym procesie** (eliminuje race: user odhacza `[x]` → push zgłasza `done` do huba → pull regeneruje plik; osobne joby miały okno, w którym pull nadpisywał akcję usera).
- **`inbox-push.mjs`** — parsuje odhaczone checkboxy z sekcji Otrzymane (markery `%% inbox:items:start/end %%`): task `[x] Zrobione` → `done` (`inbox-client.done`, hub dokłada reply); query/reply `[x] Zapoznane` → `done`. Archiwum całych nitek w `Zasoby/inbox-archive/YYYY-MM.md`. Idempotentny (domknięcie idempotentne po stronie huba).
- **`inbox-pull.mjs`** — renderuje wątki (z `inbox-client.pull`) jako callouty Obsidiana (redesign 07.2026: inline HTML spany `os-*` stylowane snippetem `skrzynka.css` w vaultcie; wzorzec `mockup-skrzynka.html`). **Kontrakt push↔pull jest święty**: bloki `> `, marker `%% id/thread %%`, checkbox `- [x] Zrobione|Zapoznane` — zmiany renderera nie mogą go ruszyć (test roundtrip).
- **`auto-reply.mjs`** — MVP autonomii: agent odpowiada na `query` z wiedzy vaulta zanim zrobi to człowiek (spawn `claude -p`, `--allowedTools Read,Glob,Grep`, `cwd`=vault — tylko odczyt, zero akcji zewnętrznych). Atomowy claim przez `inbox-client.claimQuery` (marker `payload.auto_reply_attempted` po stronie huba) PRZED spawnem; kontrakt `NO_ANSWER` (gdziekolwiek w odpowiedzi) → query zostaje człowiekowi; reply tagowane `🤖 auto-odpowiedź asystenta` + `payload.auto_reply`. Jeden kandydat per run. Historia append-only w `auto-replies-YYYY-MM.md`. Reużywa `resolveClaudeBin`/`buildCleanEnv` z `lib/claude-spawn.js`.
- **`env-loader.mjs`** — wspólny loader `.env` dla wszystkich skryptów inbox (jedna implementacja = koniec driftu). Kontrakt: po `loadEnv()` ZAWSZE ustawione `INBOX_TODO_PATH`, `INBOX_SKRZYNKA_PATH`, `INBOX_ARCHIVE_DIR` albo czytelny błąd konfiguracji.

**Świadomie odrzucona opcja minimalna (decyzja trwała — nie wracamy)**: „zostawiamy Postgres, dodajemy TLS + role per user" — tańsza (bez zmian transportu w klientach), ale odrzucona, bo (a) zostawia connection stringi Postgresa w onboardingu osób nietechnicznych (największy punkt tarcia), (b) brak odwoływalnych tokenów per osoba zarządzalnych z Pulsa, (c) utrzymuje publiczny port bazy (TLS szyfruje, ale powierzchnia ataku = pełny protokół Postgresa, nie 5 endpointów z rate limitem), (d) utrzymuje zależność `pg`. Odrzucono także **wspólny tailnet zespołu** (dashboard Pulsa bez autoryzacji = RCE między członkami) i **Tailscale node-sharing** (ręczne ACL-e w konsoli — poza zasięgiem nietechnicznych; domyślnie wystawia port huba). W topologii ról odrzucone trwale: **sync na obu maszynach** (fabryka plików konfliktowych) i **sync wyłącznie na VPS** — kusi (Skrzynka zawsze aktualna, także na telefonie), ale kupuje to cichym gubieniem `[x] Zrobione`; awaria przez nieaktualność jest widoczna i samonaprawialna, awaria przez cofnięcie akcji usera podkopuje zaufanie. Wracamy do tego **dopiero po** uszczelnieniu `pull` (scalanie zamiast nadpisywania).

## `server.js` — HTTP i granice bezpieczeństwa

Ręczny router na czystym `node:http` (bez frameworka), match po `segments`/`method`. Serwuje `public/` (SPA fallback, ETag/no-cache dla kodu, 1 h cache dla logo/favicon). Kluczowe reguły:

- **Proxy `/api/vps/*` → instancja VPS** — dashboard lokalny przełącza widok między `local` a `vps` bez osobnego portu.
- **Blokada zewnętrzna**: request z nagłówkiem `X-Forwarded-For` (czyli przez Tailscale Funnel) dostaje 403 na wszystkim poza `/webhook/*`, `/ask/*` i `/inbox/v1/*`. Dashboard jest dostępny **tylko** przez Tailscale (prywatnie); publiczne są wyłącznie webhooki, endpoint głosowy i tokenowe endpointy skrzynki. **Kontrakt kolejności matcherów: webhook → ask → inbox → guard XFF → api/static** — publiczne endpointy (webhook/ask/inbox) MUSZĄ stać przed guardem (inaczej Funnel dostaje 403 i endpoint jest martwy), a guard przed api/static (inaczej dashboard — w tym prywatne `/api/inbox/members` — robi się publiczny).
- **`POST /ask/:token`** (publiczny, opt-in `ASK_ENABLED=1` — bez niego 403): podwójna autoryzacja token z URL + nagłówek `X-Secret` (`timingSafeEqual`, oba porównania zawsze — czas odpowiedzi nie zdradza, czy token trafiony). Kody błędów TYLKO dla intruzów (403/405/413 bez szczegółów); wszystko „dla człowieka" = 200 text/plain z tekstem (Shortcuts gubi body przy kodzie błędu). Body czytane własnym `readTextBody` (surowy tekst, nie `parseBody`-JSON) z capem 64 KB — bez limitu nieuwierzytelniony intruz streamowałby setki MB → OOM schedulera (body idzie PRZED autoryzacją).
- **Inbox — publiczne vs prywatne**: tokenowe endpointy skrzynki `/inbox/v1/:token/*` (ping/pull/done/send/claim-query) są **publiczne** (przez Funnel, PRZED guardem XFF — patrz kontrakt matcherów). Administracja członkami `/api/inbox/members` (GET/POST/DELETE) jest **prywatna**: siedzi ZA guardem XFF (Tailscale-only, ruch z Funnela z `X-Forwarded-For` nigdy tu nie dotrze) i dodatkowo ma **guard cross-origin** (`isCrossOriginRequest`: `Origin ≠ Host` na żądaniach mutujących → 403) — te endpointy zwracają/obsługują SEKRETY (pełny token, kod zaproszenia), a globalne `ACAO:*` pozwoliłoby stronie `evil.com` czytać odpowiedź z `localhost`; XFF tego nie łapie (żądanie z przeglądarki idzie bez XFF). POST zwraca pełny token JEDNORAZOWO (GET zawsze maskuje), fail-fast 503 gdy brak `WEBHOOK_BASE_URL` (kod zaproszenia byłby bezużyteczny) PRZED utworzeniem członka.
- **Settings powiadomień**: `GET/PUT /api/settings/notifications` (GET zawsze zamaskowany; PUT whitelist 3 kluczy state, tylko stringi, pusty string czyści klucz → fallback env wraca) oraz `POST /api/settings/notifications/push-to-vps` — push robi **serwer** (czyta pełne wartości z własnego state/env), dashboard nigdy nie operuje pełnymi sekretami; statusy: 503 brak VPS, 400 nic do wysłania, 502 pad pusha.
- Przy starcie `reapOrphanedRuns()` oznacza osierocone runy `running` (po crashu/restarcie) jako `killed` — inaczej kill-bar w UI wisiałby w nieskończoność.

## Frontend (`public/`)

Vanilla JS, zero frameworka i buildu. `app.js` (duży, stanowy) + wydzielone czyste helpery `enum-map.js` i `render-helpers.js` (jedyne z testami — logika kalendarza, sparkline, podpisy poll). Polling co 3 s z guardem: liczy tani podpis payloadu i pomija `innerHTML`, gdy nic się nie zmieniło. Timeouty w UI są w minutach, w bazie/executorze w ms (`msToMin`/`minToMs`).

## Pułapki (udokumentowane w `docs/solutions/`)

- **SQLite granica doby w `localtime`**: porównania "dziś" rób `date(col,'localtime') = date('now','localtime')` — goły `date('now')` liczy w UTC i przesuwa dobę o offset strefy.
- **Top-N per grupa = window function**: N ostatnich runów per job przez `ROW_NUMBER() OVER (PARTITION BY job_id ...)`, nie globalny `LIMIT` (jedna szybka grupa zjadłaby całe okno).
- **Instalator `curl|bash` / `irm|iex`**: stdin to pipe z treścią skryptu, nie klawiatura — interaktywne `read` dostaje EOF. Handoff do interaktywnego procesu przez `/dev/tty` (Unix) / `CONIN$` (Windows). Testuj ZAWSZE przez prawdziwy pipe, nie lokalne `bash install.sh`.
- **Entry-point guard w Node**: porównuj przez `fs.realpathSync` po obu stronach — macOS symlinkuje `/var`,`/tmp` do `/private/*`. Skrypt `.ps1` puszczany przez `iex` trzymaj w czystym ASCII (BOM/diakrytyki łamią parser PS 5.1).
